# NeuroStars Games Tracker — структура и пошаговый план реализации

## 1. Цель проекта

Создать простой сайт-трекер, который:

- принимает результаты из разных обучающих игр;
- связывает каждую попытку с учеником и конкретной игрой;
- хранит историю попыток в Cloud Firestore;
- позволяет администратору войти по Email/Password и посмотреть учеников и их результаты;
- размещается как статический сайт на GitHub Pages;
- позволяет подключать новые игры через один небольшой общий модуль.

На первом этапе не нужны отдельный сервер, сложные роли пользователей, фреймворк или система управления школой. Достаточно HTML, CSS, JavaScript и Firebase Web SDK.

---

## 2. Как будет работать система

### Для ученика

1. Учитель формирует персональную ссылку на игру, например:

   `https://example.github.io/forest-trails/?student=s001`

2. Ученик открывает ссылку. Ничего вводить не нужно.
3. Игра считывает параметр `student` из адресной строки.
4. Игра незаметно выполняет Firebase Anonymous Authentication.
5. После завершения игра рассчитывает результат.
6. Общий модуль отправляет одну запись о попытке в коллекцию `gameResults`.
7. Игра показывает ученику обычный экран завершения.

### Для администратора

1. Администратор открывает страницу трекера.
2. Входит через Firebase Authentication с Email/Password.
3. Видит список учеников и краткую сводку результатов.
4. Выбирает ученика и видит историю его попыток по всем играм.
5. При необходимости фильтрует попытки по игре.

### Общая схема

```text
Персональная ссылка
        ↓
Обучающая игра на GitHub Pages
        ↓  Anonymous Authentication
Общий модуль отправки результата
        ↓
Cloud Firestore: gameResults
        ↑
Административный трекер на GitHub Pages
        ↑  Email/Password Authentication
Администратор
```

## 3. Предлагаемая структура Firestore

Нужны три основные коллекции: `students`, `games` и `gameResults`.

### 3.1. Коллекция `students`

Один документ — один ученик. Идентификатор документа совпадает с техническим `studentId`.

Путь тестового ученика:

`students/s001`

Пример полей документа:

| Поле | Тип | Обязательное | Назначение |
|---|---|---:|---|
| `studentId` | string | да | Технический ID, например `s001` |
| `displayName` | string | да | Имя, которое видит только администратор |
| `active` | boolean | да | Можно ли принимать новые результаты ученика |
| `createdAt` | timestamp | да | Дата создания записи |
| `notes` | string | нет | Необязательная заметка администратора |

Пример:

```text
students/s001
  studentId: "s001"
  displayName: "Тестовый ученик"
  active: true
  createdAt: <server timestamp>
```

Почему `studentId` используется и как ID документа, и как поле: путь `students/s001` удобно проверять в правилах безопасности, а отдельное поле упрощает экспорт и чтение данных.

### 3.2. Коллекция `games`

Один документ — одна подключенная игра. Идентификатор документа совпадает с уникальным `gameId`.

Для первой игры предлагается стабильный ID:

`games/forest-trails`

Пример полей:

| Поле | Тип | Обязательное | Назначение |
|---|---|---:|---|
| `gameId` | string | да | Уникальный постоянный ID игры |
| `title` | string | да | Название для трекера, например `Forest Trails` |
| `active` | boolean | да | Принимаются ли результаты этой игры |
| `url` | string | да | Адрес игры на GitHub Pages |
| `createdAt` | timestamp | да | Дата подключения |
| `description` | string | нет | Короткое описание |

Важно: `gameId` нельзя менять после подключения игры. Название и URL можно менять, но история попыток всегда должна ссылаться на прежний `gameId`.

### 3.3. Коллекция `gameResults`

Один документ — одна завершенная или явно зафиксированная попытка. ID документа Firestore создает автоматически.

Пример пути:

`gameResults/AbCdEf123...`

Поля результата:

| Поле | Тип | Обязательное | Назначение |
|---|---|---:|---|
| `studentId` | string | да | Ссылка на ученика, например `s001` |
| `gameId` | string | да | Ссылка на игру, например `forest-trails` |
| `correctAnswers` | number | да | Количество правильных ответов |
| `totalTasks` | number | да | Общее количество заданий |
| `errors` | number | да | Количество ошибок |
| `percentage` | number | да | Результат от 0 до 100 |
| `durationSeconds` | number | да | Время прохождения в секундах |
| `completed` | boolean | да | Завершена ли попытка |
| `createdAt` | timestamp | да | Серверные дата и время записи |
| `authUid` | string | да | UID анонимной Firebase-сессии, отправившей результат |
| `resultVersion` | number | да | Версия формата результата, сначала `1` |

Необязательные поля на будущее:

| Поле | Тип | Назначение |
|---|---|---|
| `startedAt` | timestamp | Время начала, если игра его фиксирует |
| `levelId` | string | Уровень или режим игры |
| `metadata` | map | Дополнительные данные конкретной игры без изменения общей схемы |

Правила расчета:

- `correctAnswers` должен быть от `0` до `totalTasks`;
- `errors` не должен быть отрицательным;
- `percentage = round(correctAnswers / totalTasks * 100)`;
- `durationSeconds` не должен быть отрицательным;
- `createdAt` должен задаваться серверным временем Firestore, а не часами устройства ученика;
- результат создается один раз и не редактируется игрой после отправки.

### Почему результаты находятся в общей коллекции

Общая коллекция `gameResults` проще для первого проекта и хорошо подходит для запросов:

- все попытки ученика: `studentId == s001`;
- попытки ученика в одной игре: `studentId == s001` и `gameId == forest-trails`;
- последние попытки: сортировка по `createdAt`;
- результаты конкретной игры: `gameId == forest-trails`.

Некоторые составные запросы потребуют индексы Firestore. Firebase покажет готовую ссылку для создания нужного индекса при первом таком запросе.

## 4. Доступ и безопасность

### 4.1. Роли

Будут два типа Firebase-пользователей:

- ученическая игра — анонимный пользователь;
- администратор — пользователь Email/Password.

Чтобы отличать администратора от обычного вошедшего пользователя, рекомендуется создать дополнительную служебную коллекцию:

`admins/{firebaseUid}`

Документ администратора создается вручную в Firebase Console после создания его Email/Password-аккаунта. Его ID — Firebase UID этого аккаунта.

Это проще для учебного проекта, чем настраивать сервер и custom claims.

### 4.2. Что должны разрешать правила Firestore

Правила безопасности следует написать так, чтобы:

- любой активный администратор мог читать `students`, `games` и `gameResults`;
- анонимно вошедшая игра могла только создать новый результат;
- игра не могла читать список учеников или историю результатов;
- игра не могла изменять или удалять уже записанные результаты;
- новый результат содержал только разрешенные поля и правильные типы данных;
- указанные `studentId` и `gameId` существовали и были активны;
- `authUid` совпадал с UID текущего анонимного пользователя;
- администраторская страница была закрыта не только интерфейсом, но и правилами Firestore.

### 4.3. Ограничение персональной ссылки

Параметр `?student=s001` удобен, но сам по себе не доказывает, что ссылку открыл именно этот ученик. Человек, который знает другой `studentId`, теоретически сможет подставить его в адрес и отправить результат от чужого имени. Anonymous Authentication подтверждает только наличие анонимной Firebase-сессии, а не личность ученика.

Для первого учебного этапа можно принять эту модель, если результаты не являются критичными оценками и ссылки передаются аккуратно. При этом правила Firestore все равно должны проверять структуру и допустимость записи.

Если позже потребуется более надежная защита, следующий уровень — выдавать каждой ссылке отдельный случайный токен и обменивать его на ограниченную серверную сессию через Cloud Function. Это потребует серверной части и поэтому не включается в первую простую версию.

### 4.4. Firebase-конфигурация в браузере

Объект `firebaseConfig` будет виден в исходном коде сайта — для Firebase Web это нормально. Защита строится не на сокрытии конфигурации, а на Authentication, Firestore Security Rules, проверке разрешенных доменов и, при необходимости, Firebase App Check.

```text
gamestracker/
├─ index.html                  # Страница входа администратора
├─ dashboard.html              # Список учеников и краткая сводка
├─ student.html                # История выбранного ученика
├─ README.md                   # Краткое описание и запуск проекта
├─ IMPLEMENTATION_PLAN.md      # Этот план
├─ css/
│  └─ styles.css               # Общие стили всех страниц
├─ js/
│  ├─ firebase-config.js       # Инициализация Firebase
│  ├─ auth.js                  # Вход, выход и проверка администратора
│  ├─ firestore.js             # Запросы к students, games, gameResults
│  ├─ login-page.js            # Логика страницы входа
│  ├─ dashboard-page.js        # Вывод списка учеников и сводки
│  ├─ student-page.js          # История попыток и фильтр по игре
│  └─ ui.js                    # Общие сообщения, формат дат, загрузка
├─ shared/
│  └─ game-reporter.js         # Общий модуль для подключения игр
├─ firestore.rules             # Версия правил безопасности в репозитории

   └─ workflows/

```

Для первой версии можно использовать обычный JavaScript без React, сборщика и npm. Это уменьшает количество настроек и делает каждый файл понятнее. Если проект значительно вырастет, структуру можно будет перенести на фреймворк позже.

GitHub Pages нормально открывает отдельные файлы `dashboard.html` и `student.html`. Это проще, чем настраивать маршруты одностраничного приложения.

## 6. Общий модуль подключения игр

Файл `shared/game-reporter.js` будет единой точкой интеграции для Forest Trails и будущих игр.

### Ответственность общего модуля

Модуль должен:

1. считать `studentId` из параметра `student` в URL;
2. проверить, что параметр присутствует и имеет допустимый простой формат;
3. инициализировать Firebase один раз;
4. выполнить Anonymous Authentication;
5. принять рассчитанные игрой данные;
6. проверить числа до отправки;
7. вычислить или перепроверить процент;
8. добавить `authUid`, `resultVersion` и серверное время;
9. создать документ в `gameResults`;
10. вернуть игре понятный результат: отправлено успешно или произошла ошибка;
11. защитить от случайной двойной отправки при повторном нажатии кнопки.

### Что остается внутри каждой игры

Каждая игра сама:

- знает свой постоянный `gameId`;
- считает правильные ответы, ошибки и общее количество заданий;
- измеряет время прохождения;
- решает, когда попытка считается завершенной;
- вызывает общий модуль один раз в момент завершения.

Предполагаемый интерфейс модуля на уровне идеи, без реализации кода:

```text
initializeGameReporter({ gameId })
submitGameResult({
  correctAnswers,
  totalTasks,
  errors,
  durationSeconds,
  completed,
  optional metadata
})
```

### Как распространять модуль

Для простоты модуль хранится в репозитории трекера и публикуется вместе с ним на GitHub Pages. Игры подключают его по полному HTTPS-адресу. Так исправления логики отправки можно делать в одном месте.

Чтобы обновление однажды не сломало все игры, формат модуля нужно версионировать. Начать можно с пути наподобие:

`https://<owner>.github.io/gamestracker/shared/v1/game-reporter.js`

В структуре выше показан короткий путь; при реализации лучше сразу создать папку `shared/v1/`.

Если загрузка общего модуля недоступна, игра должна продолжить работать как игра, но показать понятное сообщение, что результат не удалось сохранить. На первом этапе автоматическую очередь повторной отправки можно не делать.

## 7. Пошаговый план реализации

### Этап 0. Зафиксировать исходные данные

Перед разработкой записать:

- Firebase Project ID;
- Web App Firebase configuration;
- GitHub-имя владельца и название репозитория трекера;
- точный URL Forest Trails;
- постоянный `gameId`: `forest-trails`;
- Email администратора;
- Firebase UID администратора;
- тестовый `studentId`: `s001`.

Не помещать пароль администратора в файлы проекта, GitHub или Firestore.

### Этап 1. Подготовить данные Firebase

1. Проверить, что в Authentication включены Email/Password и Anonymous.
2. Создать администратора с Email/Password в Firebase Console.
3. Скопировать его UID.
4. Создать документ `admins/{uid}`.
5. Проверить или создать документ `students/s001`.
6. Добавить документ `games/forest-trails` с названием и URL игры.
7. Убедиться, что `active` у ученика и игры равно `true`.

Результат этапа: Firebase знает тестового ученика, первую игру и разрешенного администратора.

### Этап 2. Подготовить каркас сайта-трекера

1. Создать перечисленные HTML-, CSS- и JS-файлы.
2. Подключить Firebase Web SDK как браузерные ES-модули.
3. Добавить `firebaseConfig` в отдельный файл.
4. Создать простую навигацию и состояния «загрузка», «ошибка», «нет данных».
5. Пока не подключать Forest Trails.

Результат этапа: страницы открываются локально через простой веб-сервер, но еще не показывают реальные данные.

### Этап 3. Реализовать вход администратора

1. На `index.html` сделать поля Email и Password.
2. Выполнить вход через Firebase Authentication.
3. После входа проверить наличие `admins/{uid}`.
4. Если документа нет, немедленно завершить сеанс и показать отказ в доступе.
5. Если документ есть, открыть `dashboard.html`.
6. На закрытых страницах повторять проверку авторизации при каждой загрузке.
7. Добавить кнопку выхода.

Результат этапа: трекер доступен только разрешенному администратору.

### Этап 4. Реализовать список учеников

1. Прочитать коллекцию `students`.
2. Показать имя и технический ID каждого ученика.
3. Добавить для каждого ученика ссылку на `student.html?student=s001`.
4. Сначала вывести простую сводку: число попыток, последняя активность и последний процент.
5. Корректно показать состояние, когда попыток еще нет.

На первом этапе список учеников можно загружать полностью. Пагинация понадобится только при заметном росте количества записей.

### Этап 5. Реализовать историю ученика

1. Считать `studentId` из URL административной страницы.
2. Загрузить документ ученика.
3. Запросить его результаты из `gameResults`.
4. Отсортировать по `createdAt` от новых к старым.
5. Показать дату, игру, правильные ответы, ошибки, процент, длительность и статус завершения.
6. Загрузить коллекцию `games`, чтобы показывать понятные названия вместо одних `gameId`.
7. Добавить фильтр по игре.
8. При необходимости создать предложенный Firebase составной индекс.

Результат этапа: администратор видит полную историю тестового ученика.

### Этап 6. Написать и проверить Firestore Security Rules

1. Запретить доступ по умолчанию.
2. Разрешить администратору чтение основных коллекций.
3. Разрешить анонимному пользователю только создание `gameResults`.
4. Проверить список полей, типы и допустимые диапазоны чисел.
5. Проверить существование активных `students/{studentId}` и `games/{gameId}`.
6. Проверить соответствие `authUid` текущему `request.auth.uid`.
7. Запретить игре чтение, изменение и удаление результатов.
8. Протестировать разрешенные и запрещенные сценарии через Firebase Emulator Suite или Rules Playground.
9. Только после тестирования опубликовать правила.

Минимальный набор негативных тестов:

- пользователь без входа пытается записать результат;
- отсутствует `studentId` или `gameId`;
- ученик или игра не существует;
- `percentage` больше 100;
- отрицательное время;
- лишние неожиданные поля;
- `authUid` не совпадает;
- анонимный пользователь пытается прочитать результаты;
- результат пытаются изменить после создания;
- Email/Password-пользователь без документа `admins/{uid}` пытается открыть данные.

### Этап 7. Создать общий `game-reporter` модуль

1. Определить версию формата результата `1`.
2. Реализовать чтение и проверку параметра `student`.
3. Реализовать анонимный вход.
4. Реализовать единственную функцию отправки результата.
5. Добавить защиту от двойного вызова в рамках одной попытки.
6. Возвращать игре понятные коды ошибок.
7. Проверить отправку на отдельной простой тестовой HTML-странице, не изменяя Forest Trails.
8. Удалить тестовую страницу после проверки или оставить ее только в локальной папке, не публикуя.

### Этап 8. Подключить Forest Trails

Этот этап выполняется позже, после отдельной команды.

1. Найти в игре место, где начинается попытка.
2. Начать измерение времени.
3. Найти единственную точку окончательного завершения.
4. Подключить версию `v1` общего модуля.
5. Указать `gameId: forest-trails`.
6. Передать итоговые показатели в `submitGameResult`.
7. Заблокировать повторную отправку при повторном клике или перезагрузке экрана завершения.
8. Показать ненавязчивое состояние «результат сохраняется» и затем успех или ошибку.
9. Пройти игру по ссылке с `?student=s001`.
10. Проверить документ в Firestore и отображение в административном трекере.
11. Проверить поведение ссылки без параметра `student`.

### Этап 9. Опубликовать трекер на GitHub Pages

### Этап 10. Провести сквозную проверку

## 8. Как подключать каждую следующую игру

Для новой игры не нужно менять основную схему Firestore.

Чек-лист подключения:

1. Выбрать короткий уникальный `gameId`, например `math-race`.
2. Никогда не использовать один `gameId` для двух разных игр.
3. Создать `games/math-race` в Firestore.
4. Подключить общий модуль `shared/v1/game-reporter.js`.
5. Указать игре ее `gameId`.
6. На завершении передать стандартные показатели.
7. При необходимости положить специфические данные в `metadata`, не меняя основные поля.
8. Проверить игру с тестовым учеником.
9. Убедиться, что результат появился в административном трекере.
10. Только после теста раздать персональные ссылки.

Пример персональной ссылки для новой игры:

`https://example.github.io/math-race/?student=s001`

## 9. Что не нужно делать в первой версии

Чтобы проект оставался понятным, пока не следует добавлять:

- React, Vue или другой фреймворк;
- собственный сервер;
- Cloud Functions только ради базовой записи результата;
- сложную аналитику и графики;
- редактирование результатов;
- автоматическое создание учеников из игры;
- хранение персональных данных внутри игровых ссылок;
- офлайн-очередь и синхронизацию;
- несколько административных ролей;
- вложенные подколлекции результатов у каждого ученика.

Эти возможности можно добавить позже, когда базовый путь «игра → Firestore → административная история» будет стабильно работать.

## 10. Критерии готовности первой версии

Первая версия считается готовой, когда:

- ученик открывает Forest Trails по ссылке и ничего не вводит;
- игра выполняет анонимный вход;
- после завершения создается ровно одна корректная запись;
- результат содержит все обязательные поля;
- серверное время используется для даты записи;
- администратор входит по Email/Password;
- посторонний Email/Password-пользователь не получает доступ;
- администратор видит список учеников;
- администратор видит историю `s001` и может отфильтровать ее по игре;
- анонимный пользователь не может читать результаты или изменять их;
- сайт и игра работают с GitHub Pages;
- подключение следующей игры требует только регистрации `gameId` и вызова общего модуля.
